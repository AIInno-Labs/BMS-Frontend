03The three translations

Rev 2 §7.1: "the prototype's display strings become a presentation concern, not a stored value." This is that concern, implemented.

STATUS PENDING ←→ "Pending" The seven UI strings map 1:1 AWAITING_MANAGER_APPROVAL ←→ "Awaiting Manager Approval" READY_TO_MANUFACTURE ←→ "Ready to Manufacture" IN_FABRICATION ←→ "In Fabrication" ON_HOLD ←→ "On Hold" COMPLETE ←→ "Complete" CANCELLED ←→ "Cancelled" The 15 PRD lifecycle labels collapse onto these seven — many-to-one, derived from JOB_STATUS_META[].group so it cannot drift. PRIORITY NORMAL ←→ "Normal" Was sending "Normal" → 400 (Jackson is case-sensitive), HIGH ←→ "High" and reading "HIGH" → silently displayed "Normal". RUSH ←→ "RUSH" RESIN ISO ←→ "Isophthalic Polyester" resin_code, seeded by migration V7. VE ←→ "Vinyl Ester" The catalogue exists because the same PHEN ←→ "Phenolic" three resins were spelled three ways.

04Status changes now go through stages

This is the part that was silently doing nothing before. stageStatus is READ_ONLY on JobDTO and recomputed by JobStageServiceImpl.recomputeJobStatus — "a cache with exactly one writer". So a status change is a stage change.

updateJob(job) │ ├─ status differs from the loaded value? │ ├─ CANCELLED → DELETE /jobs/{id} │ └─ otherwise → GET /jobs/{id}/stages find stageKey │ PUT /jobs/{id}/stages/{id} move it │ GET /jobs/{id} re-read the bumped version │ ├─ PUT /jobs fields + id + version └─ PUT /jobs/{id}/job-card?version= the card, replaced as a unit Stage keys, from recomputeJobStatus: approval complete → READY_TO_MANUFACTURE production in-progress → IN_FABRICATION completed complete → COMPLETE production blocked → ON_HOLD

Re-reading the version is conditional, deliberately. A stage move bumps the row, so the token the edit was loaded with goes stale through no fault of the user — that case re-reads. Re-reading unconditionally would refresh past a genuinely concurrent edit and quietly defeat the optimistic lock, which is the exact lost-update problem Rev 2 §06 added @Version to prevent. When no stage moved, the loaded version is sent as-is and a real conflict surfaces as 409.

05Job numbers now come from the frontend

This one is a backend change as well — the frontend could not have done it alone.

Before: JobDTO.jobNumber was @JsonProperty(access = READ_ONLY), so Jackson dropped it inbound and create() never read it. Every factory job got a sequence value like JOB-0007, and the number typed into the create drawer was silently discarded.

After: the field is writable on create. A supplied number is used; omitting it still allocates from SequenceGeneratorService. Quote-derived jobs remain JOB-Q-{quoteNumber}.

RuleWhere enforced
No prefix required — JOB-1101, 1101, A-22/B all valid Only the character set and length are checked: ^[A-Za-z0-9._-]+$, ≤ 64 chars (matching job_number VARCHAR(64) in V3). Same rule on both sides.
Unique per organization Three layers: the drawer checks loaded jobs, existsByJobNumberAndOrganizationId checks the tenant, and uk_job_org_job_number is the backstop for the check-then-insert race.
Upper-cased on the server Postgres compares text case-sensitively, so without this job-1101 and JOB-1101 would both insert and the numbers would not actually be unique. Normalising buys case-insensitive uniqueness with no functional index.
Immutable after create update() already had this guard — it was dead code while the field was READ_ONLY and always arrived null. It is live now.

Duplicates return a clean 409

With numbers coming from the client, collisions go from near-impossible to routine, so the error path started to matter.

before — same failure, two different answers
- app-level check → OperationNotPermittedException → 400
- lost the race → DataIntegrityViolationException → 409, body containing
'duplicate key value violates unique constraint "uk_job_org_job_number"'
after
+ both paths → 409, businessErrorCode 306,
"That job number is already used in this organization"
+ raw constraint text is logged, not returned

New DuplicateResourceException renders as 409 rather than reusing OperationNotPermittedException: a duplicate is not a malformed request, and the caller's remedy is a different value rather than a corrected one.

Two things the operator should know. The drawer's suggested number (max + 1) is derived only from the jobs this browser has loaded — one capped page — so with more jobs than that, or two people creating at once, it will propose one that is taken. It is a starting point, not an allocation; the 409 is the real answer. Leaving the field empty is the only collision-free option, since the sequence generator allocates server-side.

Also: manual numbers and the sequence share one namespace. Type JOB-1101 while the sequence sits at JOB-0007 and nothing breaks now, but the sequence will eventually reach 1101 and that create will fail as a duplicate. Advancing the sequence past a manually-supplied number would fix it — not done here, as it needs a floor-setting API the generator does not expose.

06All counts come from GET /jobs/counts

Frontend-only change. Every KPI tile, donut segment and stage card now reads one org-wide aggregate instead of tallying the array this browser happens to hold.

The tiles were under-reporting, and would have got worse. They counted the loaded jobs array — one page, now capped at 200 (it was requesting 500, which the contract caps at 200 anyway). A tenant with 250 jobs saw "ACTIVE JOBS" computed from 200 of them. The number sat directly above a table drawn from the same partial list, so nothing looked wrong.

JobCountsDTO aggregates in the database across the whole organization, so it stays right regardless of page size.

The fallback matters because /jobs/counts carries JOB_READ like everything else: a role without it, or an older backend, would otherwise blank every tile to zero. Falling back to the loaded page keeps them plausible — and authoritative: false records that they are a floor rather than a total, if you later want to surface that in the UI.

07Two silent failures, now loud

context/JobsContext.tsx — refreshJobs
- if (e.status === 403 || e.status === 401 || e.status === 500) {
- setJobs([]); setError(null); return []; // renders as "no jobs"
+ if (e instanceof FrpApiError && e.status === 403) {
+ setError("You do not have access to jobs. If you are an organization
+ admin, the JOB_* privileges may not be granted to your role yet.");

That swallow was hiding the highest-priority backend bug. PrivilegeCatalogSynchronizer reconciles newly-discovered JOB_*, QUOTE_* and STAGE_ADVANCE codes onto SUPER_ADMIN only; for ORG_ADMIN it back-fills exactly one code, INTEGRATION_PARAM_MANAGE. Any org admin whose role predates the job module holds none of the job privileges, and the interceptor is deny-by-default.

The frontend will now say so. The backend fix is still required — a one-method change in PrivilegeCatalogSynchronizer.java:112 to grant all non-platform ACTION codes, matching what org provisioning already does at creation time. Until it lands, an existing tenant still sees no jobs.

lib/frp/job-mapper.ts — priority and version
- if (value === "Normal" || value === "High") return value; // "NORMAL" fell through
- return "Normal"; // HIGH displayed as Normal
+ return PRIORITY_TO_UI[value.trim().toUpperCase()] ?? "Normal";
+ if (job.version == null) throw new Error(`Job ${job.id} has no version —
+ refresh before saving, or the backend will reject the write.`);

09How to verify

# backend cd frp && ./mvnw spring-boot:run # Postgres on :5432, API on :8080/api/v1 # frontend cd FRP-frontend && npm run dev # :3000 # already passing ./node_modules/.bin/tsc --noEmit # 722 files, 0 errors, strict Then, signed in as a user holding JOB_READ: /jobs list loads, status and priority correct, assignee resolves /jobs/[id] card loads; Save persists; Print opens status edit moves the stage, badge follows, audit row appears create no /customers call; company resolved from the name

If the job list is empty and shows the access message, that is the privilege back-fill, not the cutover. Confirm with GET /auth/me — rolesPrivileges will not contain JOB_READ. Granting it to the ORG_ADMIN role, or applying the synchronizer fix, resolves it.
